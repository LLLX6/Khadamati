# تقرير الأمان لمشروع خدماتي

**تاريخ الفحص:** 26 يوليو 2026
**النطاق:** الكود الحالي، اختبارات API، الإعدادات، ملفات النشر، الحزم المتعقبة وسجل Git
**الفرع:** `release/production-readiness`

## 1. الملخص

يحتوي المشروع على ضوابط أمنية جيدة قياسًا إلى بنيته الحالية: Hash للجلسات والرموز، صلاحيات خادمية، CORS مقيد، تحقق من توقيع ملفات الوسائط الخاصة، حدود لأحجام الطلبات، قفل لمحاولات الدخول، OTP محدود، Audit Log، ومنع واضح للوصول المتقاطع في المسارات التي يغطيها الاختبار.

لا يمثل هذا الفحص شهادة اختراق مستقلة. المخاطر الأعلى المتبقية هي استمرارية البيانات، تخزين Bearer Token في المتصفح مع JavaScript مضمّن، غياب Rate Limit مركزي موزع، غياب Foreign Keys ومigrations عامة، وعدم وجود بيئة staging خارجية لاختبار التزامن.

## 3. المصادقة والجلسات

### تم التحقق منه

- الجلسة تستخدم Token عشوائيًا.
- الخادم يحفظ `SHA-256` للـToken، لا القيمة الخام.
- انتهاء الجلسة يؤدي إلى إبطالها.
- تسجيل الخروج يبطل الجلسة.
- تغيير PIN يبطل الجلسات الأخرى للحساب.
- PIN مخزن بـPBKDF2-SHA256 و160,000 دورة.
- تسجيل الدخول يطبق قفلًا بعد المحاولات المتكررة.
- الحساب غير النشط لا يستعيد جلسة صالحة.
- رمز التطوير OTP لا يُكشف أو يُقبل كقيمة ثابتة في production.

### خطر متبقٍ: Token في LocalStorage

الواجهة تحفظ Bearer Token محليًا للمحافظة على الجلسة بعد إغلاق PWA. أي XSS ناجح قد يقرأه. توجد CSP، لكنها تسمح بـ`unsafe-inline` لأن معظم التطبيق داخل `index.html`.

**الحالة:** 🔴 يحتاج قرارًا معماريًا. الحل الأفضل على المدى المتوسط هو نقل المصادقة إلى Cookie من نوع `Secure`, `HttpOnly`, `SameSite` مع حماية CSRF، أو فصل JavaScript المضمّن وإزالة `unsafe-inline` قبل الإطلاق الواسع. لا يُنفذ هذا كتعديل سريع لأنه قد يكسر الجلسات الحالية.

## 4. الصلاحيات وIDOR

### تم التحقق منه

- مسارات الإدارة تستخدم `require_admin(permission)`.
- مسارات المزود تستخدم جلسة مزود وصلاحيات عضو الفريق.
- المستخدم يرى ويعدل طلباته المملوكة له.
- المحادثات مرتبطة بالطلب وأطرافه.
- وثائق المزود وملفات الطلب الخاصة تستخدم روابط موقعة.
- فحص API يمنع تعديل فرع أو عضو فريق لمزود آخر.
- حالة التواصل لا تكشف الهاتف قبل موافقة مستقلة.
- دور الحساب يأتي من الجلسة الخادمية، وليس من قيمة يرسلها العميل.

### حدود الفحص

تم اختبار المسارات الحرجة الآلية، ولم ينفذ Penetration Test بشري شامل لكل تركيب معرف ممكن. يلزم فحص متخصص قبل معالجة بيانات حساسة على نطاق واسع.

## 5. API والتحقق من المدخلات

### الموجود

- SQL بمعاملات Parameterized في المسارات التي تمت مراجعتها.
- قوائم سماح للحالات والأدوار والصلاحيات.
- حدود لأجسام JSON.
- تحقق من الأنواع والقيم في عمليات الإدارة الحساسة.
- منع إعادة Foundation مرتين.
- تحقق خادمي من مبلغ الدفع وتوقيع Webhook.
- OTP ومحاولات الدخول والاسترداد والترشيحات لها حدود.
- أخطاء API عامة ولا تُرجع Stack Trace للمستخدم.

### مخاطر متبقية

1. بعض مسارات الصور تقبل JSON/Base64 حتى 60MB، ما قد يستهلك ذاكرة كبيرة.
2. لا يوجد Rate Limiter مركزي موزع لكل عمليات الكتابة.
3. ThreadingHTTPServer مناسب للحجم الحالي والتجربة، لكنه ليس بديلاً عن بنية WSGI/ASGI مدارة تحت حمل كبير.
4. Idempotency موجود في مسارات عمل محددة، لكنه ليس عقدًا عامًا لكل POST.

**الحالة:** 🟡 تحتاج قياسًا في staging وخطة تحسين دون تخمين حمل production.

## 6. CORS وHeaders

الخادم يرسل:

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: SAMEORIGIN`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy`
- `Content-Security-Policy`
- HSTS عند وصول `X-Forwarded-Proto: https`
- CORS فقط للأصول الموجودة في `KHADAMATI_ALLOWED_ORIGINS`

لا يرسل `Access-Control-Allow-Credentials` لأن المصادقة الحالية Bearer Token وليست Cookies.

ملاحظة CSP: `unsafe-inline` باقٍ للسكريبت والأنماط بسبب بنية الملف الواحد. إزالة هذا الاستثناء تتطلب فصلًا منظمًا واختبارات.

## 7. الملفات والصور

تم التحقق آليًا من:

- فحص توقيع MIME، لا الامتداد فقط.
- رفض ملف غير متوافق.
- روابط موقعة للوسائط الخاصة.
- مدة للرابط الموقّع.
- منع تخزين API والوسائط الخاصة في Service Worker.
- رفض Symlinks في أداة Backup.
- منع Zip Path Traversal في Restore.

ما يحتاج تحسينًا لاحقًا:

- إزالة EXIF والموقع من الصور المرفوعة إذا لم تكن مطلوبة.
- فحص Malware خارجي للوثائق عند زيادة الاستخدام.
- تخزين كائنات خاص بصلاحيات بدل القرص المحلي.

هذه الخطوات تحتاج خدمة أو قرار بنية ولم تُنفذ تلقائيًا.

## 8. الدفع وOTP وWebhooks

- لا تُخزن بيانات بطاقات.
- المبلغ الموثوق يأتي من كتالوج الخادم.
- الاشتراك لا يُفعل بوهم نجاح عند غياب التحقق.
- Webhook يحتاج توقيعًا صحيحًا.
- OTP في production يحتاج قناة إرسال حقيقية.
- رمز التطوير لا يعمل كرمز إنتاج ثابت.
- الأسرار موجودة كأسماء فقط في `.env.example`.

**الحالة:** 🟡 منطق الحماية موجود.
**غير مثبت:** تكامل بوابة دفع أو قناة OTP إنتاجية؛ لا يجوز وصفهما بالإنتاجيين قبل المفاتيح واختبار الخادم.

## 9. فحص الأسرار

تم فحص الملفات المتعقبة وسجل Git بأنماط قوية للمفاتيح الخاصة ومفاتيح OpenAI وGitHub وAWS.

- لم يظهر سر حقيقي وفق الأنماط المستخدمة.
- ظهرت قيم وهمية فقط داخل الاختبارات.
- لم تُعرض أي قيمة محتملة في التقرير.

الفحص الآلي لا يضمن اكتشاف كل صيغة مخصصة. يُنصح بتفعيل Secret Scanning وPush Protection في GitHub إن كانت الخطة تسمح.

## 11. السجلات والأحداث الحساسة

- يوجد `audit_logs` للتعديلات الإدارية والمالية الحساسة.
- سجلات HTTP أصبحت JSON منظمة وتحمل Request ID والمسار دون Query والحالة والمدة.
- كل استجابة تحمل `X-Request-ID`.
- لا تسجل طبقة HTTP PIN أو Token أو OTP أو Body أو Query أو موقعًا دقيقًا.
- سجلات WhatsApp الجديدة تخفي رقم الهاتف ولا تخزن رد البوابة الكامل.
- لا توجد منصة مراقبة أو سياسة احتفاظ مثبتة.

**الحالة:** ✅ Structured Logging منفذ. ربط خدمة خارجية وسياسة الاحتفاظ يحتاجان موافقة وحسابًا مملوكًا للمالك.

## 13. الحوادث الأمنية

عند الاشتباه بحادث:

1. صنف الحادث واحفظ الأدلة دون نشر بيانات شخصية.
2. أوقف المسار المتأثر أو اعزل الخدمة عند الضرورة.
3. ألغِ Tokens والمفاتيح المتأثرة واستبدلها من لوحات الخدمات.
4. لا تكتب القيم الجديدة داخل Git أو المحادثات.
5. استعد من Backup مجربة إذا تأثرت سلامة البيانات.
6. راجع Audit Logs وسجلات الخادم.
7. أخطر المستخدمين والجهات المختصة فقط وفق التزام قانوني مؤكد.
8. وثق السبب والإصلاح والاختبارات.
9. اطلب مختص أمن وخصوصية عند وجود تسريب حقيقي.
