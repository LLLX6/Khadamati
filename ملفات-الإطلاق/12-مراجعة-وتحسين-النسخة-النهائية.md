## الفرق بين الموجود والمطلوب

### موجود ويجب تطويره دون تكراره

- مسودة طلب محلية واستعادتها.
- إعادة الطلب من طلب سابق.
- قائمة انتظار للخدمات غير المتاحة.
- تقويم أسبوعي وتوفر أساسي للمزود.
- عروض ومقارنة عروض ومحادثة مرتبطة بالطلب.
- حالات طلب أساسية ووصول المزود.
- صور قبل وبعد في ملف المزود.
- بلاغات جودة وتقييم موثق.
- تقارير تشغيلية وإحصاءات مزود وإدارة أولية.

### ناقص أو غير مركزي

- لا توجد آلة حالات مركزية تمنع الانتقالات غير الصحيحة وتسجل تاريخها.
- لا يوجد سجل زمني خادمي للطلب يمكن تدقيقه من الطرفين والإدارة.
- لا توجد بطاقة اتفاق بإصدار وموافقة مستقلة من الطرفين.
- لا يوجد ملف ممتلكات أو أجهزة مرتبط بصاحب الطلب وسجل خدمتها.
- لا يوجد إثبات تسليم مرتبط بالطلب مع قرار العميل.
- إكمال الطلب يغلقه مباشرة ولا يمر بحالة انتظار تأكيد العميل.
- منع الطلب المكرر يعتمد على الواجهة ولا توجد Idempotency خادمية.
- توفر المزود لا يطبق طاقة استيعابية يومية عند المطابقة.
- تحليل فجوات الطلب حسب الخدمة والمنطقة محدود.

## عوائق خارج نطاق التعديل الآمن

- استمرارية SQLite والملفات على Render تحتاج بيئة Staging وتخزينًا دائمًا.
- النسخ الاحتياطي الخارجي المجدول يحتاج حسابًا ووجهة يملكها المالك.
- الانتقال الكامل من Bearer Token في LocalStorage إلى HttpOnly Cookies يحتاج
  قرار استضافة متوافقًا مع GitHub Pages وCORS.
- المراقبة الخارجية واختبار الاختراق البشري يحتاجان خدمات أو مختصين خارجيين.

## خطة التنفيذ

1. إضافة مخطط متوافق للخدمات الجديدة دون تعديل البيانات القديمة.
2. إنشاء خدمات نطاق مركزية للحالة والاتفاق والممتلكات والتسليم.
3. ربطها بمسارات API الحالية مع تحقق ملكية وصلاحيات.
4. إضافة Idempotency لإنشاء الطلب.
5. تطوير التوفر ليشمل السعة اليومية.
6. عرض الميزات داخل تجربة الهاتف الحالية دون إنشاء صفحات مكررة.
7. إضافة اختبارات نطاق وAPI وواجهة، ثم إعادة المجموعة الكاملة.

## نتيجة التنفيذ

اكتملت التحسينات الآمنة على الإصدار `v63` من دون تغيير إطار العمل أو حذف
البيانات القديمة. التغيير البنيوي الوحيد إضافة جداول وعمود اختياريين؛ لذلك
تظل الطلبات والحسابات والاشتراكات السابقة قابلة للقراءة.

### ما تم إصلاحه وتطويره

- أضيفت آلة حالات مركزية وسجل أحداث غير قابل للتعديل لكل طلب.
- أصبح الاتفاق ذا رقم إصدار، وتأكيد منفصل للمستخدم والمزود، وإلغاء تلقائي
  للتأكيدين عند تعديل التفاصيل.
- أضيف إثبات إنجاز بصور قبل/بعد، ثم قرار العميل: تم الحل أو مراجعة الجودة.
- رُبط بلاغ الجودة بالطلب والمزود والعميل ومنع إنشاء البلاغ نفسه مرتين.
- أضيفت ملفات خاصة بالمستخدم للمنازل والمركبات والأجهزة مع سجل خدمتها.
- أضيف منع خادمي لتكرار الطلب عند إعادة المحاولة بالمفتاح نفسه.
- أصبحت السعة اليومية للمزود جزءًا من المطابقة الفعلية.
- أضيفت مؤشرات تشغيلية للمزود وفجوات طلب وتغطية للإدارة.
- أصبحت إعادة الطلب نسخة جديدة مستقلة، ولا تحمل حالة أو محادثة أو صور الطلب
  السابق.
- حدثت واجهة الهاتف ودورة الطلب ونسخة `public` وService Worker إلى `v63`.

## قيود لم تُخفَ

- لم يتم النشر العام أو تعديل بيئة Render أو الدمج في `main`.
- قاعدة التطوير الحالية تحتوي سجلات عرض تجريبية، ولا تصلح كنسخة إنتاج.
- فحص بيئة Python العامة وجد إصدارات قديمة من `Pillow` و`pip` على الجهاز؛
  ليست ضمن `requirements.txt` ولا يستوردها التطبيق، وتحتاج تحديثًا مستقلًا
  لبيئة التطوير قبل اعتمادها كبيئة بناء مشتركة.
- تشغيل SQLite في الاستضافة يحتاج قرصًا دائمًا ونسخًا احتياطيًا خارجيًا
  مجدولًا قبل اعتماد الإنتاج.
- المراقبة الخارجية واختبار الاختراق البشري لم ينفذا لأنهما يحتاجان حسابًا أو
  مختصًا يختاره المالك.
- الانتقال إلى Cookies من نوع HttpOnly يحتاج قرار استضافة وCORS مستقلًا؛ لم
  يُنفذ كتغيير معماري داخل هذه المهمة.
