# عقد الإصدار وPWA والتخزين الدائم — v1.2.0

التاريخ: 2026-08-23
النطاق: مرشح إصدار مكتمل على فرع مشتق من جاهزية الإنتاج؛ لم يحدث نشر أو تغيير DNS أو بيانات إنتاج وقت هذا الختم.

## ما تغير

- رُفع اسم cache إلى `khadamati-app-shell-v1.2.0-r1` في نسختي Service Worker المتطابقتين.
- لا تصبح نسخة Service Worker الجديدة صالحة للتثبيت إذا فشل تحميل أي ملف أساسي؛ تبقى النسخة المكتملة السابقة عاملة.
- حذف cache القديم محصور بمفاتيح خدماتي التي تبدأ بـ`khadamati-app-shell-v` ولا يمس caches أخرى.
- لا يُخزن رد التنقل داخل `index.html` إلا إذا كان ناجحاً، من نوع `text/html`، وليس ملفاً مرفقاً، وكان التنقل إلى المسار الأساسي أو `index.html`.
- مُنع fallback غير المتصل لمسارات API والوسائط الخاصة والرفع والتنزيل والتصدير وملفات PDF/ZIP/Office.
- قُصر runtime cache على أصول ثابتة من نفس الأصل لا تحمل `no-store` أو `private`.
- أصبحت كتابة cache جزءاً من Promise الاستجابة نفسها؛ لا يُستدعى `event.waitUntil` متأخراً بعد رجوع طلب الشبكة.
- يُقبل فقط معامل إصدار ثابت اسمه `v` وبقيمة محدودة، ثم يحذف من مفتاح cache. بذلك تعمل روابط CSS وJavaScript المرقمة عند انقطاع الشبكة دون إنشاء cache غير محدود.
- أُضيف `assets/scripts/khadamati-ui-state.js` إلى app shell وإلى فحص تطابق المرآة.
- توسع فحص المرايا ليشمل `index.html` وService Worker وmanifest وCSS وسكربتي visuals وui-state.
- أصبح اعتماد المزود خادميًا ومركزيًا: رقم سجل/ترخيص، تاريخ صلاحية، ووثيقتان؛ تغيير دليل الهوية أو المسار القانوني يعيد الحساب إلى `under_review` ويوقف الظهور واستقبال الطلبات حتى المراجعة.
- أصبحت مناطق كل خدمة تضيق تغطية الحساب ولا تستطيع توسيعها أو تجاوز حدود الباقة عبر API مباشر.
- يعاد فحص الأهلية والاشتراك والخدمة والمنطقة وتوقيت عُمان والسعة والحظر عند تحرير الإرسال المؤجل وعند قبول الطلب أو العرض داخل معاملة ذرية.
- أُضيفت أعمال ما بعد Commit للرسائل الخارجية وحذف الوسائط؛ لا تُنفذ عند Rollback أو فشل Commit.
- فُصلت صلاحيات منصة الإدارة للقانون والمخاطر والسيناريوهات المالية ومفاتيح Enterprise.
- يفرض Blueprint المصادقة الثنائية للإدارة في الإنتاج ويترك مفتاحها ومفاتيح Web Push أسرارًا يضبطها المالك.
- ضُبط Render ليتابع `release/production-readiness` مع تعطيل النشر التلقائي، وفحص `/readyz`، وقرص دائم واحد تحت `/var/data/khadamati` لمسارات قاعدة البيانات والرفع والنسخ الاحتياطي.
- أُضيف `tests/test_release_contract.py` لفحص الإصدار والمرايا وحواجز PWA وعقد Render.
- حُدث `README.md` و`RELEASE_NOTES.md` لعرض المرشح `v1.2.0 / r1` بصدق، دون ادعاء أنه نُشر أو أن الخطة المدفوعة فُعّلت.

## حدود وقرارات لازمة

- القرص الدائم في Render يتطلب instance مدفوعاً؛ لذلك يحدد Blueprint خطة `starter` لكنه يعطل النشر التلقائي. لم يُطبق Blueprint ولم تُفعّل الخطة أو التكلفة ضمن هذه التغييرات المحلية.
- مرجع القرار: [Render Persistent Disks](https://render.com/docs/disks) يوضح أن القرص للخدمات المدفوعة، و[Render Free Web Services](https://render.com/docs/free) يوضح أن SQLite والرفع المحلي يضيعان عند إعادة التشغيل أو النشر في الخدمة المجانية.
- يجب أخذ نسخة احتياطية من بيانات Render الحالية قبل تركيب القرص أو تغيير مسار قاعدة البيانات؛ القرص الجديد يبدأ فارغاً، ولا يجوز افتراض انتقال ملفات البيئة المؤقتة تلقائياً.
- يلزم نجاح GitHub Actions على Commit المراجعة نفسه قبل الدمج أو النشر، رغم نجاح جميع البوابات المحلية.
- لا يحتوي `render.yaml` على قيم أسرار؛ المتغيرات الحساسة ما زالت `sync: false`.
- القرص الجديد يبدأ فارغًا، ووجود `/readyz=200` لا يثبت انتقال البيانات. قبل تطبيق Blueprint يجب نسخ قاعدة الإنتاج والرفع، استعادتهما على القرص، مقارنة الأعداد، إبقاء Rollback، وتجربة استعادة خارجية منفصلة. النسخ الموجودة على القرص نفسه لا تكفي وحدها للتعافي من فقد القرص.
