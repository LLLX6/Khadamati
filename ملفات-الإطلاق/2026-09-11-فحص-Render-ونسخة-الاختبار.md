أُنشئت مفاتيح مستقلة عشوائية للإدارة والتوقيع والتوثيق الثنائي داخل إعدادات خدمة الاختبار فقط. لا توجد قيمها في Git أو هذا التقرير. يظل تفعيل التوثيق الثنائي للمشرف مطلوبًا عند إعداد حسابه؛ لم يُعطَّل هذا الشرط لإظهار جاهزية غير حقيقية. لم يُربط SMTP أو APNs/FCM أو دفع فعلي بهذه البيئة.

أوامر Render المنفذة:

```bash
pip install -r requirements.txt
python server.py
```

نتائج التحقق:

- اكتمل تثبيت الاعتماديات والبناء والنشر بنجاح.
- سجل الخادم `service.started` ببيئة `staging` والإصدار `1.3.1` والمنفذ `10000`.
- سجل Render طلبَي `HEAD /` و`GET /` بحالة HTTP 200.
- ظهرت مقاييس تشغيل CPU والذاكرة بعد النشر؛ هذه عينات بدء تشغيل وليست اختبار حمل.
- تعطل استعلام السجلات مرة بخطأ خدمة Loki، ثم نجحت إعادة الاستعلام ضمن فترة أقصر. لم يكن ذلك خطأً مُثبتًا في التطبيق.
- الفحوص الآلية السابقة محفوظة في [بوابة الجودة](https://github.com/LLLX6/Khadamati/actions/runs/34437899019) و[بناء الهاتف](https://github.com/LLLX6/Khadamati/actions/runs/34437899003). لم يتغير كود التطبيق في هذه الجولة، ولم تُعد الفحوص السابقة بلا سبب.
- لم تُختبر جلسة متصفح أو رحلة عميل كاملة على رابط Render الجديد، ولم تُثبت جاهزية `/readyz`. لا تزال اختبارات أجهزة iPhone وAndroid الفعلية مطلوبة.

## ما يلزم قبل تحديث الإنتاج

1. تحديد ما إذا كانت الخدمة الحالية تحتوي بيانات عملاء أو طلبات حقيقية، ثم إثبات وجود نسخة خارجية كاملة إذا كانت موجودة. لا تكفي نسخة داخل القرص المؤقت نفسه.
2. حفظ قاعدة SQLite والملفات المرفوعة بأداة النسخ الأصلية، وفحص البصمة وتجربة الاسترجاع في مسارات فارغة. أدوات النسخ والاسترجاع المجهزة في `scripts/backup_sqlite.py` و`scripts/restore_sqlite_backup.py` لا تُنفّذ الآن على الإنتاج.
3. تفعيل خطة خدمة تدعم قرصًا دائمًا وإرفاق قرص على `/var/data/khadamati` بعد تأمين البيانات. إضافة القرص أو تغيير الاستضافة قد يعيد النشر؛ لا تنفذهما أولًا على أمل حفظ الملفات الحالية.
4. نقل البيانات والتحقق منها قبل توجيه التطبيق إلى المسارات الجديدة. القيم المستهدفة: قاعدة البيانات `/var/data/khadamati/database/khadamati.sqlite3`، والرفع `/var/data/khadamati/uploads`، والنسخ `/var/data/khadamati/backups`.
5. التحقق من مفاتيح الإنتاج وتوثيق المشرف الثنائي والبريد، ثم نشر الكود المختبر وفحص `/readyz` قبل فتح الاستخدام العام. تُطابق الواجهة والخادم وحزم الهاتف في خطوة الإصدار نفسها.

الاتصال المتاح يدعم قراءة الخدمة والسجلات والنشر وإعداد متغيرات البيئة، لكنه لا يوفر تعديل خطة الخدمة أو إرفاق القرص أو استخراج ملفات SQLite. ولا يوجد Render CLI موثق في بيئة العمل. كذلك لا تدعم خدمات Free الوصول إلى Shell/SSH. مسار `/api/backup` في التطبيق ينشئ نسخة على الخادم ويعرض بياناتها الوصفية فقط، ولا ينزّل قاعدة البيانات والملفات إلى المالك. إذا كانت هناك بيانات فعلية دون نسخة خارجية، يلزم تأمين مسار استخراج مع Render قبل أي إجراء يعيد تشغيل الخدمة.

تنبيه تشغيلي محدد: خدمات Free لا تسمح بالاتصالات الصادرة على منافذ SMTP المعتادة، ومنها `587` المستخدم في إعداد البريد المجهز. لذلك لا يكفي ضبط كلمة مرور البريد على الخطة الحالية لإثبات عمل رسائل الإدارة.

## أثر هذه الجولة وحدودها

أُنشئت خدمة اختبار واحدة على الخطة المجانية باستخدام حصة الحساب المجانية؛ لم تُشترَ خطة مدفوعة. لم تُعدّل خدمة خدماتي الحالية أو خدمات الحساب الأخرى، ولم يُدمج شيء في `main` أو فرع الإنتاج. لم تُنفذ ترحيلات أو حذف أو استرجاع على بيانات الإنتاج. تُراجع تكلفة الخطة والقرص في لوحة Render قبل تفعيلهما.

الوصول إلى Render أصبح متاحًا. أما حسابا Apple Developer وGoogle Play Console وتوقيع المتاجر والخصوصية والإشعارات والمشتريات واختبار الأجهزة فتبقى متطلبات إطلاق مستقلة موضحة في [تقرير تجهيز الهاتف](2026-09-09-تجهيز-تطبيقات-الهاتف.md).
