# جاهزية Render والتخزين الدائم — Khadamati v1.1.1

تاريخ المراجعة: 10 أغسطس 2026
النطاق: إعداد تشغيلي فقط؛ لم يُنفذ نشر، ولم تُغيّر خطة Render، ولم يُنشأ قرص مدفوع.

## القرار المختصر

- أصبح مسار فحص Render في `render.yaml` هو `/readyz` بدلاً من `/healthz`.
- يبقى `/healthz` فحصاً بسيطاً لحياة العملية، بينما `/readyz` هو بوابة استقبال الحركة لأنه يفحص اتصال SQLite وإعداد مسارات الإنتاج وقابلية كتابة التخزين الأساسي.
- لا يجوز اعتماد API للإنتاج قبل أن يعيد `/readyz` حالة HTTP `200` و`"ok": true`.
- لم نضف `disk` إلى `render.yaml` ولم نغيّر `plan: free`. القرص الدائم متاح لخدمة Render مدفوعة ويتطلب قراراً صريحاً من المالك لأنه يغيّر التكلفة وحالة الحساب.

## لماذا هذا التغيير آمن

تعد Render أي استجابة `2xx` أو `3xx` نجاحاً لفحص HTTP، وأي `4xx` أو `5xx` فشلاً. عند نشر نسخة جديدة، لا تحول Render الحركة إليها حتى تنجح فحوص الجاهزية؛ وإذا لم تنجح خلال المهلة تلغي النشر وتبقي النسخة السابقة. لذلك يمنع `/readyz` تشغيل نسخة جديدة على تخزين مؤقت أو ناقص الإعداد بدلاً من إظهار نجاح مضلل.

> تنبيه تشغيلي: الخدمة الحالية على الخطة المجانية لن تصبح جاهزة لمستخدمي إنتاج حقيقيين بمجرد تغيير المسار. يلزم أولاً تنفيذ قائمة الإعداد التالية بموافقة المالك. لا تغيّر الفحص إلى `/healthz` لتجاوز الخطأ.

## الإعداد المطلوب في Render بعد موافقة المالك

1. ترقية خدمة `khadamati-app-api` إلى Web Service مدفوعة تدعم Persistent Disk.
2. إرفاق قرص واحد بالخدمة من صفحة **Disks** في Render.
3. ضبط Mount Path المطلق على:

   ```text
   /var/data
   ```

4. اختيار أصغر حجم يغطي قاعدة البيانات والوسائط والنسخ الاحتياطية مع مساحة نمو آمنة. يمكن زيادة الحجم لاحقاً، ولا يمكن تقليله حسب Render.
5. ضبط متغيرات البيئة التالية من لوحة Render، وليس بإيداع أسرار في Git:

   ```text
   KHADAMATI_DB_PATH=/var/data/khadamati.sqlite3
   KHADAMATI_UPLOAD_DIR=/var/data/uploads
   KHADAMATI_BACKUP_DIR=/var/data/backups
   ```

6. التأكد من ضبط أسرار الإنتاج المطلوبة، ومنها `KHADAMATI_OTP_PEPPER` أو `KHADAMATI_MEDIA_SIGNING_KEY`، وأي متطلبات 2FA مفعلة، دون تسجيل قيمها في المستودع أو تقرير الإطلاق.
7. بدء نشر مراقب بعد أخذ نسخة احتياطية قابلة للاسترجاع من أي بيانات حالية مهمة.
8. التحقق من:

   ```text
   GET https://khadamati-app-api.onrender.com/healthz  -> 200
   GET https://khadamati-app-api.onrender.com/readyz   -> 200 و ok=true و issues=[]
   ```

## ما يجب حفظه على القرص

| البيانات | المسار | السبب |
|---|---|---|
| قاعدة SQLite | `/var/data/khadamati.sqlite3` | الحسابات والطلبات والمحادثات وحالات الأعمال |
| المرفقات | `/var/data/uploads` | الصور والإثباتات والملفات الخاصة المرتبطة بصفوف القاعدة |
| النسخ المنطقية | `/var/data/backups` | استرجاع SQLite بصورة متسقة واختبار الترحيلات |

فقط الملفات المكتوبة تحت Mount Path تبقى بعد إعادة التشغيل أو النشر. نظام الملفات خارج `/var/data` مؤقت ويمكن أن يفقد تغييرات وقت التشغيل.

## قيود القرص التي تؤثر في القرار

- القرص الدائم يتطلب خدمة مدفوعة.
- يمكن لخدمة واحدة ومثيل واحد الوصول إليه؛ لا يمكن توسيع خدمة مرتبطة بقرص إلى عدة مثيلات.
- Build وPre-deploy وOne-off Jobs لا تصل إلى قرص الخدمة، لذلك لا تُشغّل النسخ الاحتياطي أو استعادة SQLite منها بافتراض وجود `/var/data`.
- إرفاق القرص يلغي النشر بلا توقف؛ تتوقف النسخة القديمة قبل بدء الجديدة لعدة ثوانٍ لحماية البيانات من الكتابة المتزامنة.
- Render تنشئ Snapshot يومياً وتحتفظ باللقطات سبعة أيام على الأقل، لكن لقطة القرص ليست بديلاً عن نسخة SQLite منطقية مجرّبة.

## سياسة النسخ الاحتياطي

### قبل كل ترحيل أو إصدار يغيّر قاعدة البيانات

1. ضع التطبيق في نافذة صيانة أو أوقف الكتابات الجديدة.
2. أنشئ نسخة SQLite متسقة باستخدام SQLite Backup API أو أداة النسخ الموجودة في المشروع؛ لا تنسخ ملف قاعدة نشط بطريقة نظام ملفات عادية.
3. احفظ النسخة داخل `/var/data/backups` باسم يحوي UTC وSHA الإصدار.
4. أنشئ قائمة تحقق تربط نسخة القاعدة بنسخة المرفقات اللازمة.
5. انقل نسخة مشفرة إلى وجهة منفصلة عن قرص Render وفق سياسة الاحتفاظ المعتمدة؛ فقدان الخدمة أو القرص يجب ألا يفقد الأصل والنسخة معاً.
6. تحقق من سلامة SQLite، ثم نفّذ استعادة تجريبية في بيئة معزولة قبل اعتبار النسخة صالحة.

### جدول مقترح يحتاج اعتماد المالك

- نسخة SQLite يومية، ونسخة إضافية قبل كل ترحيل.
- احتفاظ يومي 14 يوماً، وأسبوعي 8 أسابيع، وشهري 12 شهراً، بعد اعتماد متطلبات الخصوصية والتكلفة.
- اختبار استعادة شهري موثق بزمن الاستعادة والنتيجة.

## إجراء الاستعادة

1. أوقف استقبال الطلبات والكتابات الجديدة.
2. سجّل وقت الحادث وSHA والنسخة المختارة دون بيانات شخصية.
3. انسخ قاعدة البيانات الحالية والمرفقات إلى منطقة حجر قبل أي استبدال.
4. تحقق من Hash وحالة النسخة ثم استعدها إلى ملف مؤقت تحت `/var/data`.
5. شغّل `PRAGMA integrity_check` واختبارات القراءة الأساسية في بيئة معزولة.
6. بدّل ملف القاعدة بصورة ذرية، وأعد المرفقات المتوافقة فقط.
7. شغّل التطبيق وتحقق من `/readyz` ثم Smoke Tests للعميل والمزود والإدارة.
8. افتح الحركة تدريجياً، واحتفظ بنسخة ما قبل الاستعادة حتى انتهاء المراجعة.

لا تستخدم Restore للقرص أثناء استمرار SQLite في الكتابة. استعادة Snapshot كاملة تفقد كل التغييرات اللاحقة للّقطة ولا تسمح Render باستعادة جزء من القرص؛ لذلك يلزم قرار حادث موثق ونافذة توقف.

## خطة الرجوع عند فشل الإصدار

1. لا تحوّل الحركة إلى الإصدار الجديد إذا لم يُرجع `/readyz` حالة `200`.
2. عند خطأ كود فقط، استخدم Rollback إلى آخر Deploy ناجح بعد تقييم توافق Schema.
3. Rollback للكود لا يعيد حالة القرص؛ القرص يحتفظ بالتغييرات بين الإصدارات.
4. عند تغيير بيانات غير متوافق، أوقف الكتابات واستعد النسخة المنطقية المأخوذة قبل الترحيل، ثم تحقق من `/readyz` وSmoke Tests.
5. عطّل Auto Deploy مؤقتاً أثناء الحادث حتى لا يعاد نشر Commit المسبب للمشكلة.
6. لا تحذف القرص أو قاعدة البيانات أو المرفقات خلال الرجوع.

## بوابة الموافقة قبل التنفيذ الخارجي

يجب أن يوافق مالك المشروع صراحةً على البنود التالية قبل أي تغيير في Render:

- الخطة المدفوعة وتكلفتها.
- حجم القرص وتكلفته وMount Path `/var/data`.
- نافذة التوقف المتوقعة عند النشر.
- وجهة النسخة المشفرة خارج Render ومدة الاحتفاظ.
- المسؤول عن النسخ، اختبار الاستعادة، والاستجابة للحوادث.

## حدود التحقق الحالي

- `/readyz` الحالي يتحقق من وجود إعدادات مسارات قاعدة البيانات والرفع والنسخ الاحتياطي في الإنتاج، ويجرب `SELECT 1`، ويتحقق من قابلية كتابة مجلد قاعدة البيانات ومجلد الرفع.
- لم نعدّل `server.py` في هذه الدفعة لتجنب التعارض مع تغييرات الخادم الجارية.
- يُوصى في دفعة خادم مستقلة بإضافة تحقق آمن من أن `/var/data/backups` موجود وقابل للكتابة، دون إنشاء أو حذف ملف في كل فحص صحة، مع اختبار API يثبت أن المسار غير القابل للكتابة يعيد `503` وسبباً عاماً بلا كشف مسارات داخلية.
- تغيير `render.yaml` هنا لم يُطبق على حساب Render ولم يبدأ Deploy.

## سجل التحقق لهذه الدفعة

| الفحص | النتيجة |
|---|---|
| قراءة `render.yaml` بواسطة PyYAML | ناجح؛ `healthCheckPath=/readyz` |
| `git diff --check -- render.yaml` والوثيقة | ناجح؛ لا أخطاء مسافات |
| مراجعة `/readyz` في مصدر الخادم | موجود ويعيد `503` عند وجود مشكلة و`200` عند اكتمال الجاهزية |
| تغيير خطة أو قرص أو متغيرات Render | لم يُنفذ |
| نشر أو إعادة تشغيل أو تعديل بيانات إنتاج | لم يُنفذ |
