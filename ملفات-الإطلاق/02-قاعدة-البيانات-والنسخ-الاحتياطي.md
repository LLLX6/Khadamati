# قاعدة البيانات والنسخ الاحتياطي

**تاريخ الفحص:** 26 يوليو 2026
**الفرع:** `release/production-readiness`
**حالة الوثيقة:** نتائج فحص وتنفيذ فعلي على نسخة محلية، وليست إثباتًا لإعداد Render الخارجي

## 1. الخلاصة

قاعدة البيانات الفعلية التي يستخدمها الخادم هي SQLite عبر مكتبة `sqlite3` القياسية في Python. ملف `postgres_schema.sql` هو مخطط مقترح للتوسع ولا يعني أن PostgreSQL مستخدم حاليًا. البيانات والصور تكون مركزية بين الأجهزة فقط عندما تتصل جميع الجلسات بنفس خادم API ونفس ملف SQLite ومجلد الرفع الدائمين.

القاعدة المحلية التي تم فحصها سليمة بنيويًا وفق `PRAGMA integrity_check`، ولم تظهر تكرارات هواتف أو سجلات يتيمة ضمن العلاقات المنطقية التي يغطيها الفاحص. لكن إعداد Render الموجود في المستودع لا يثبت وجود قرص دائم، ولذلك تبقى استمرارية بيانات البيئة المنشورة **غير مثبتة وتمنع اعتماد الإطلاق العام**.

## 4. المخطط والفهارس

المخطط يُنشأ داخل `init_db()` في `server.py`. توجد فهارس للمسارات الأكثر استخدامًا، منها:

- حالة وتاريخ الطلبات.
- ترشيحات الطلب حسب الطلب والمستخدم.
- الإشعارات حسب نوع الحساب والمعرف وحالة القراءة.
- Hash الجلسة وتاريخ الانتهاء.
- توزيع الطلبات حسب موعد الإطلاق والمزود.
- موافقات التواصل.
- الاشتراكات والدفعات.
- OTP حسب الهاتف والغرض.

لا توجد علاقات Foreign Key معرفة في مخطط SQLite الحالي. فُعّل `PRAGMA foreign_keys=ON` لكل اتصال جديد، لكنه لن يفرض علاقات غير معرفة. إضافة العلاقات إلى القاعدة الحالية تغيير مخطط كبير يحتاج Migration منفصلة، فحص بيانات، نسخة احتياطية، واختبار رجوع؛ لذلك لم تُنفذ في هذه المهمة تلقائيًا.

## 5. Migrations

الوضع الحالي:

- الجداول والحقول الناقصة تُنشأ أو تُضاف عند بدء الخادم بواسطة `init_db()` و`ensure_column()`.
- ترحيل الاشتراكات يعمل مرة واحدة بالمفتاح `KHADAMATI_SUBSCRIPTION_MIGRATION_V1`.
- ينشئ الخادم نسخة SQLite قبل ترحيل الاشتراكات إذا كانت القاعدة موجودة ولم يسجل المفتاح.
- لا توجد سلسلة Migrations مرقمة عامة ولا أمر منفصل للترقية أو التراجع.

هذا الأسلوب متوافق مع البيانات القديمة، لكنه غير كافٍ كإدارة مخطط إنتاجي طويلة المدى. المقترح قبل الإطلاق:

1. تثبيت نسخة مخطط Baseline.
2. تحويل كل تعديل لاحق إلى Migration مرقمة لها `up`, تحقق، وخطة `down` أو استعادة.
3. تشغيل التحقق على نسخة staging من Backup.
4. منع تنفيذ Migration خطرة تلقائيًا أثناء بدء الخدمة.

لم تُحوّل البنية الآن إلى Alembic أو ORM لأن ذلك تغيير معماري يحتاج موافقة وخطة نقل.

## 6. ما تم تنفيذه

### ✅ اتصالات SQLite أكثر أمانًا

- مهلة اتصال 12 ثانية.
- `PRAGMA busy_timeout=12000`.
- `PRAGMA foreign_keys=ON`.

هذه التحسينات تقلل أخطاء القفل القصيرة، لكنها لا تجعل SQLite مناسبًا تلقائيًا لأحمال كتابة كبيرة أو لعدة نسخ خادم.

### ✅ منع بيانات العرض في قواعد الإنتاج الجديدة

المتغير:

```text
KHADAMATI_SEED_SAMPLE_DATA=false
```

يمنع زرع المزودين والمراجعات التجريبية عند إنشاء قاعدة إنتاج جديدة. لم تُحذف أي بيانات موجودة.

### ✅ أداة فحص غير معدلة للبيانات

`scripts/audit_database.py` تفحص السلامة والتكرار والسجلات اليتيمة دون طباعة صفوف أو بيانات شخصية.

### ✅ نسخة احتياطية قابلة للتحقق

`scripts/backup_sqlite.py`:

- تستخدم SQLite Backup API بدل نسخ ملف مفتوح مباشرة.
- تضيف ملفات الرفع اختياريًا.
- تنشئ `manifest.json`.
- تسجل SHA-256 للقاعدة وكل ملف.
- تنتج ZIP وبصمة منفصلة.
- ترفض اتباع Symlinks داخل مجلد الرفع.

مثال:

```powershell
python scripts/backup_sqlite.py \
  --database /var/data/khadamati.sqlite3 \
  --uploads /var/data/uploads \
  --output /var/data/backups/khadamati-backup-YYYYMMDDTHHMMSSZ.zip
```

### ✅ استعادة آمنة إلى مسار جديد

`scripts/restore_sqlite_backup.py`:

- تتحقق من مسارات ZIP لمنع Path Traversal.
- تتحقق من كل بصمات SHA-256.
- تشغل `PRAGMA integrity_check`.
- ترفض الكتابة فوق قاعدة أو مجلد موجودين.

مثال اختبار معزول:

```powershell
python scripts/restore_sqlite_backup.py \
  --archive backup.zip \
  --database-target restored/khadamati.sqlite3 \
  --uploads-target restored/uploads \
  --confirm RESTORE_TO_EMPTY_TARGET
```

### ✅ اختبار تلقائي للنسخ والاستعادة

`tests/test_backup_restore.py` يغطي:

- دورة Backup ثم Restore للقاعدة والصورة.
- مطابقة البيانات والبصمات.
- رفض الكتابة فوق هدف موجود.

## 7. خطة النسخ الاحتياطي المقترحة

هذه الخطة **مقترحة وتحتاج اعتمادًا وربطًا بوجهة مستقلة**:

- نسخة يومية مشفرة من SQLite والملفات.
- الاحتفاظ اليومي 14 يومًا.
- نسخة أسبوعية لمدة 8 أسابيع.
- نسخة شهرية لمدة 12 شهرًا إذا سمحت السياسة القانونية والتكلفة.
- تخزين نسخة واحدة على الأقل خارج نفس خدمة Render والقرص.
- اختبار استعادة شهري إلى بيئة معزولة.
- تسجيل نتيجة الاستعادة دون نسخ بيانات شخصية إلى السجلات.
- تقييد الوصول لموظفين مخولين فقط.

يجب تحديد RPO وRTO تجاريًا قبل الإطلاق. لم يُخترع رقم ضمان غير متفق عليه.

## 8. إجراء الاستعادة المقترح

1. إيقاف عمليات الكتابة أو وضع الخدمة في صيانة.
2. حفظ نسخة من الحالة المتضررة للتحقيق.
3. اختيار Backup مكتملة البصمة.
4. الاستعادة إلى مسار جديد، لا فوق الملف الحالي.
5. تشغيل فحص السلامة والتكرار والسجلات اليتيمة.
6. تشغيل Unit وAPI Smoke على النسخة المستعادة.
7. تبديل المسار بعد موافقة المسؤول.
8. مراقبة الأخطاء ثم توثيق الحادث.
9. الاحتفاظ بخطة رجوع إلى الملف السابق.

## 9. البيانات الحساسة والوصول

| البيانات | الوصول المتوقع |
|---|---|
| وثائق المزود | الإدارة المخولة وروابط موقعة قصيرة العمر |
| هاتف المستخدم | المستخدم نفسه، والإدارة المخولة، والمزود بعد موافقة محددة |
| رسائل الطلب | أطراف الطلب والإدارة المخولة عند الحاجة التشغيلية |
| PIN | لا يُحفظ نصًا؛ Hash فقط |
| Tokens | Hash في الخادم؛ الرمز الخام لدى العميل فقط |
| OTP | Hash مع مدة ومحاولات محدودة |
| المدفوعات | بيانات الحالة والمرجع فقط؛ لا تُخزن بيانات بطاقة |

## 10. المخاطر المتبقية

### 🔴 يحتاج قرارًا وموافقة

- إثبات أو إنشاء قرص دائم على Render.
- اختيار قاعدة إنتاجية: SQLite على قرص دائم كمرحلة انتقالية أو PostgreSQL.
- اختيار تخزين دائم للصور.
- اختيار وجهة Backup خارجية مملوكة للمالك أو المؤسسة.
- حذف أو أرشفة بيانات العرض الحالية.

### ⚠️ لم يُثبت

- أن قاعدة Render الحالية موجودة على قرص دائم.
- أن الصور الحالية تستمر بعد إعادة نشر الخدمة.
- وجود Backup خارجي أو اختبار استعادة للبيئة المنشورة.
- قدرة SQLite الحالية تحت حمل إنتاجي متعدد المستخدمين.

## 11. طريقة التراجع

التغييرات المنفذة لا تحذف أو تحول بيانات:

- يمكن تعطيل فحص البيانات التجريبية بإعداد بيئة التطوير فقط.
- أدوات Backup/Restore مستقلة ولا تغير الخادم.
- إعدادات SQLite الجديدة لا تغير المخطط.
- في حال فشل أي إصدار، تُستخدم نسخة قاعدة سابقة مجربة ويعاد نشر Commit سابق على staging بعد موافقة المسؤول.

## 12. المطلوب من المالك

1. فتح لوحة Render والتحقق من `KHADAMATI_DB_PATH`, `KHADAMATI_UPLOAD_DIR`, `KHADAMATI_BACKUP_DIR` دون إرسال قيمها في المحادثة.
2. تأكيد هل يوجد Persistent Disk حاليًا.
3. اختيار ملكية وجهة النسخ الاحتياطية.
4. تقرير إبقاء SQLite مؤقتًا أو إعداد مشروع PostgreSQL منفصل.
5. الموافقة قبل حذف بيانات العرض أو ترحيل قاعدة الإنتاج.
